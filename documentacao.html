Auditoria Automática de Produtos com Trigger no MySQL

Este documento apresenta a arquitetura do banco de dados loja_atividade, o dicionário de dados, o funcionamento da trigger trg_produto_update e o fluxo de integração com a aplicação web.

1. Objetivo do Sistema

Garantir a rastreabilidade de alterações críticas no catálogo de produtos (nome, descrição, preço e quantidade em estoque) diretamente na camada de banco de dados, evitando que modificações passem sem registro mesmo que ocorram fora da aplicação principal.

2. Modelo Relacional & Dicionário de Dados

Tabela: produtos

Coluna Tipo Restrições Descrição
idINTPK, AUTO_INCREMENT, NOT NULLIdentificador único do produto
nomeVARCHAR(150)NOT NULLNome comercial do item
descricaoTEXTNULLEspecificações ou detalhes adicionais
precoDECIMAL(10,2)NOT NULLValor unitário em reais
quantidadeINTNOT NULLSaldo atual disponível em estoque

Tabela: historico_alteracoes

Coluna Tipo Restrições Descrição
idINTPK, AUTO_INCREMENT, NOT NULLIdentificador do evento de auditoria
id_produtoINTFK → produtos(id), NOT NULLProduto que sofreu alteração
data_alteracaoDATETIMEDEFAULT CURRENT_TIMESTAMPData e hora exata da modificação
campo_alteradoVARCHAR(50)NOT NULLNome da coluna modificada
valor_antigoTEXTNULLConteúdo anterior ao UPDATE
valor_novoTEXTNULLNovo conteúdo gravado após o UPDATE

3. Funcionamento da Trigger (trg_produto_update)

  • Evento: AFTER UPDATE ON produtos (executada automaticamente após cada linha atualizada com sucesso).
  • Granularidade: FOR EACH ROW (avalia individualmente cada registro modificado).
  • Operador <=> (NULL-safe equal): utilizado em IF NOT (OLD.campo <=> NEW.campo) para garantir que alterações envolvendo valores NULL (como preencher ou limpar a descricao) também sejam detectadas corretamente.
  • Registro Granular: se dois campos forem alterados no mesmo UPDATE (ex.: preço e quantidade), a trigger gera dois registros distintos em historico_alteracoes, identificando cada coluna modificada.

4. Código SQL da Trigger

CREATE TRIGGER `trg_produto_update` AFTER UPDATE ON `produtos` FOR EACH ROW
BEGIN
    IF NOT (OLD.nome <=> NEW.nome) THEN
        INSERT INTO historico_alteracoes (id_produto, data_alteracao, campo_alterado, valor_antigo, valor_novo)
        VALUES (NEW.id, NOW(), 'nome', OLD.nome, NEW.nome);
    END IF;

    IF NOT (OLD.descricao <=> NEW.descricao) THEN
        INSERT INTO historico_alteracoes (id_produto, data_alteracao, campo_alterado, valor_antigo, valor_novo)
        VALUES (NEW.id, NOW(), 'descricao', OLD.descricao, NEW.descricao);
    END IF;

    IF NOT (OLD.preco <=> NEW.preco) THEN
        INSERT INTO historico_alteracoes (id_produto, data_alteracao, campo_alterado, valor_antigo, valor_novo)
        VALUES (NEW.id, NOW(), 'preco', OLD.preco, NEW.preco);
    END IF;

    IF NOT (OLD.quantidade <=> NEW.quantidade) THEN
        INSERT INTO historico_alteracoes (id_produto, data_alteracao, campo_alterado, valor_antigo, valor_novo)
        VALUES (NEW.id, NOW(), 'quantidade', OLD.quantidade, NEW.quantidade);
    END IF;
END;

5. Arquitetura da Aplicação

O front-end utiliza HTML5, CSS3 e Bootstrap 5, comunicando-se via PHP 8 (PDO com Prepared Statements) ao banco MySQL 8. Toda a lógica de auditoria permanece desacoplada do código PHP, residindo integralmente no SGBD através da trigger.
